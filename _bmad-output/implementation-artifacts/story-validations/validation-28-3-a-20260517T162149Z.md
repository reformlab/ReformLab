## 🚨 Critical Issues (Must Fix)

### 1. `keep_current` Writeback Semantics Unspecified (Data Corruption)

**Impact:** Silent data corruption in multi-year runs. Year 1 incumbents replaced with "keep_current" for all non-switching households. Year 2+ have no memory of pre-existing technology.
**Source:** `domain_utils.py:99-106`, AC-1, AC-2

**Problem:**
The story's proposed implementation (Task 1.2–1.6) writes `chosen_list` values unconditionally to the incumbent column. For any household that chose `keep_current` (i.e., decided NOT to switch), `incumbent_heating` would be overwritten with the string `"keep_current"`.

Example of the failure:
- Year 1: household has `incumbent_heating = "heat_pump_air"`, chooses `keep_current` → incumbent written as `"keep_current"`
- Year 2: `DiscreteChoiceStep` reads `incumbent_heating = "keep_current"` → cost computation uses "keep_current" as the incumbent type (wrong; should be "heat_pump_air")

This directly violates AC-2 ("year 2's discrete-choice step uses 'heat_pump_air' as its incumbent technology").

The same issue applies to `EligibilityMergeStep`'s `default_choice`: ineligible households receive `chosen = "keep_current"` from the merge, and if this is written back to the incumbent, their actual technology history is erased (violating AC-7).

**Recommended Fix:**
Add a `non_update_id: str = "keep_current"` parameter (or check against `domain_config.non_purchase_ids`) to the incumbent writeback logic. Skip writeback for any row where `chosen_list[i] == non_update_id`. The incumbent column retains its existing value for those rows.

```python
# In the incumbent writeback block (after Task 1.2 loop):
incumbent_values = []
existing_incumbents = table.column(incumbent_col_name).to_pylist() if incumbent_col_name in table.column_names else [None] * n

for i in range(n):
    chosen = chosen_list[i]
    if chosen == "keep_current":  # or: chosen in non_purchase_ids
        # Retain existing incumbent (don't overwrite)
        incumbent_values.append(existing_incumbents[i] if existing_incumbents[i] is not None else "keep_current")
    else:
        incumbent_values.append(chosen)
```

This is also the correct behavior for AC-7: ineligible households receive `default_choice = "keep_current"` from `EligibilityMergeStep`, so skipping writeback on `keep_current` automatically preserves their incumbents.

### 3. AC-7 Eligibility Invariance Claim is Factually Incorrect

**Impact:** Developer will implement incorrect behavior trusting the story's false claim; AC-7 test will pass in unit tests but fail in integration tests.
**Source:** `eligibility.py:263-420`, story Dev Notes "Eligibility Invariance Pattern"

**Problem:**
The story states:
> "The existing `apply_choices_to_population()` already handles this correctly via the `choice_result.chosen` alignment with `eligible_indices`."

This is false. The actual mechanism is `EligibilityMergeStep` (in `eligibility.py`), which runs BETWEEN `logit_choice` and `StateUpdateStep`. It expands N_eligible choices to N_total by filling ineligible rows with `default_choice` (typically `"keep_current"`).

The current `apply_choices_to_population()` function at line 102-106 performs a dimension check:
```python
if len(chosen_list) != n:
    raise DiscreteChoiceError(...)
```

This dimension check requires that ChoiceResult has N_total entries — which is satisfied ONLY when `EligibilityMergeStep` has already run. No "alignment via eligible_indices" exists in `apply_choices_to_population()`.

The incumbent writeback consequences:
- Ineligible households receive `chosen = "keep_current"` from the merge step
- If writeback writes "keep_current" to their incumbent, actual technology state is lost (violates AC-7)
- Critical Issue #1's fix (skip writeback on "keep_current") also fixes AC-7 — both issues share the same root cause and solution

**Recommended Fix:**
1. Correct the false claim in Dev Notes. Replace with: "Eligibility invariance is achieved indirectly: `EligibilityMergeStep` must run before `StateUpdateStep`, expanding ineligible households' choices to `default_choice='keep_current'`. The incumbent writeback rule (skip rows where `chosen == 'keep_current'`) then preserves incumbents for ineligible households automatically."
2. Add to pipeline ordering docs: `StateUpdateStep.depends_on` must include `"eligibility_merge"` when eligibility filtering is active.
