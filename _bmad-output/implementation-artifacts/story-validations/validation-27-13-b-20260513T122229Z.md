### 1. Missing Requirement: manuallyEditedScenarioNames not cleared on create/clone

**Impact:** HIGH - Could cause new scenarios to be incorrectly marked as manually edited
**Source:** frontend/src/contexts/AppContext.tsx:652-658, Task 1

**Problem:**
The `manuallyEditedScenarioNames` Set accumulates scenario IDs but is never cleared (except on delete at lines 841-847). When `createNewScenario()` creates a scenario with `crypto.randomUUID()`, the new ID is added to the Set in `cloneCurrentScenario` (line 652-658) but NOT in `createNewScenario`. This creates an inconsistency where:
- Cloned scenarios are always marked as manually edited (intentional, per line 651 comment)
- New scenarios are NOT marked as manually edited (intentional, for auto-naming)
- But if the Set contains stale IDs, new scenarios could be incorrectly protected

**Example disaster:**
1. User creates scenario A, manually edits name → A.id added to Set
2. User deletes scenario A → A.id removed from Set (good, line 841-847)
3. User creates scenario B → B.id is NOT added to Set (good, allows auto-naming)
4. User clones scenario C → C.id added to Set (good, clone name is manual)
5. User creates scenario D → D.id is NOT added to Set

But what if step 2 doesn't happen (scenario never deleted)? The Set keeps growing forever. Eventually, `crypto.randomUUID()` could theoretically generate a collision (unlikely but non-zero probability).

**Recommended Fix:**
Add to Task 1: "In `createNewScenario()`, after creating the new scenario, verify that `newScenario.id` is NOT in `manuallyEditedScenarioNames` Set. If it is (due to collision or stale data), remove it to allow auto-naming."

Or better: "Clear the entire `manuallyEditedScenarioNames` Set in `createNewScenario()` to ensure clean state for the new scenario. This prevents any false positives from stale IDs."

### 2. AC-3 Ambiguous: Expected behavior for manually edited scenarios not specified

### 3. AC-4 Undefined Edge Cases: Restore protection doesn't handle rapid changes or async loading

**Impact:** HIGH - Implementation could have race conditions or miss user intent
**Source:** Task 3.3-3.5, AC-4

**Problem:**
Task 3 proposes using a ref flag `restoredFromStorage` that is cleared after the first effect run. This approach has edge cases:

**Edge Case 1: Rapid population changes**
1. User restores scenario with empty populationIds
2. Default selection effect runs, sets selectedPopulationId
3. User changes population to "Population B" (explicit selection)
4. Auto-name effect runs with `restoredFromStorage = true`
5. Name doesn't update (protected by flag)
6. Flag clears after first run
7. User changes population to "Population C" again
8. Auto-name effect runs again, but flag is now cleared → name updates

Should step 8 update the name? User has now changed population twice - is the second change "explicit" enough to clear protection?

**Edge Case 2: Async population loading**
1. User restores scenario with empty populationIds
2. Populations load asynchronously 500ms later
3. Default selection effect runs, sets selectedPopulationId
4. Auto-name effect runs with `restoredFromStorage = true`
5. Flag clears after 1 second (per Task 3.4)
6. User changes population 800ms after restore (during flag window)
7. Flag hasn't cleared yet → name doesn't update
8. Flag clears at 1 second
9. User changes population again at 1.2 seconds → name updates

Is this the intended behavior? The flag window creates a "protected period" that could confuse users.

**Recommended Fix:**
Specify edge case handling in AC-4:

**AC-4 (revised):** "Given a restored scenario with populationIds: [], when the default-selection effect later sets selectedPopulationId:
  - The auto-name effect distinguishes between default selection (implicit) and explicit user selection (user clicked population in UI)
  - Only the FIRST explicit user selection clears the restore protection
  - Subsequent explicit selections trigger auto-naming normally
  - Handle async loading: the protection should only apply if the selectedPopulationId change happens within 100ms of restore (debounce rapid changes)"

Implementation suggestion: Instead of a timeout-based flag, track whether the population change came from the default-selection effect vs user action. Use a ref `isDefaultPopulationSelection: boolean` that is set to true in the default-selection effect (line 465-469) and checked in the auto-name effect.

### 1. Alternative to timeout-based flag clearing for AC-4

**Value:** More reliable edge case handling

**Suggestion:**
Instead of using a timeout to clear the `restoredFromStorage` flag (Task 3.4), consider using a "first meaningful population change" detection:

```typescript
const restoredScenarioRef = useRef<string | null>(null);
const isFirstSelectionAfterRestore = useRef(false);

// In initialization effect:
if (saved) {
  restoredScenarioRef.current = saved.id;
  isFirstSelectionAfterRestore.current = true;
}

// In auto-name effect:
if (restoredScenarioRef.current === activeScenario?.id) {
  if (isFirstSelectionAfterRestore.current) {
    // Skip rename for first selection after restore
    return;
  }
}

// In setSelectedPopulationId wrapper or explicit selection handler:
// Clear flag when user explicitly changes population
const setSelectedPopulationIdExplicit = (id: string) => {
  if (restoredScenarioRef.current === activeScenario?.id) {
    isFirstSelectionAfterRestore.current = false;
  }
  setSelectedPopulationId(id);
};
```

This approach is more deterministic than a timeout and handles async loading better.

### 2. Consider using a Map instead of Set for manuallyEditedScenarioNames

**Value:** Better debugging and future extensibility

**Suggestion:**
The `manuallyEditedScenarioNames` Set only tracks IDs. Consider using a Map that tracks ID + timestamp:
```typescript
const [manuallyEditedScenarios, setManuallyEditedScenarios] = useState<Map<string, number>>(
  () => new Map(Object.entries(getManuallyEditedNamesFromStorage()))
);
```

Benefits:
- Can query "when was this scenario manually edited?"
- Can implement "expire manual edits after N days" policy
- Better debugging (can see edit history)

Downside: More complex state management. Current Set approach is simpler and sufficient for current needs.
