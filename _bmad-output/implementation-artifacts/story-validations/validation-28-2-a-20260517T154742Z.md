### 3. Alternative ID mismatch between legacy domain and new technology set

**Impact:** The integration test (Task 5.7) will fail. Any population column validated against `DEFAULT_TECHNOLOGY_SET` will have IDs that don't match the legacy `HeatingInvestmentDomain`.

**Source:** `src/reformlab/discrete_choice/heating.py:80-116` vs `src/reformlab/discrete_choice/technology_set.py:168-216`

**Problem:**
- `HeatingInvestmentDomain` (used by `DiscreteChoiceStep`): alternatives are `keep_current`, `gas_boiler`, `heat_pump`, `electric`, `wood_pellet`
- `DEFAULT_HEATING_TECHNOLOGY_SET` (from Story 28.1): alternatives are `keep_current`, `condensing_boiler`, `heat_pump_air`, `heat_pump_ground`, `district_heating`

These are fundamentally different sets. The migration maps `heating_type` values to the NEW IDs (`condensing_boiler`, `heat_pump_air`) but the legacy domain uses OLD IDs (`gas_boiler`, `heat_pump`). When `DiscreteChoiceStep` runs using the legacy `HeatingInvestmentDomain` domain, the `ChoiceSet` will contain old IDs, and the validation against `TechnologySet.domains["heating"]` will use new IDs. They will never match.

**Recommended Fix:**
Explicitly state which set of IDs is canonical for this story. If the new `DEFAULT_HEATING_TECHNOLOGY_SET` IDs are canonical, then `default_heating_domain_config()` in `heating.py` must also be updated to use the new IDs. Add this to the Modified Files list. If old IDs remain canonical, update the `DEFAULT_HEATING_TECHNOLOGY_SET` in `technology_set.py` (from Story 28.1) to match.

### 4. `validate_population_for_technology_set` type signature violates mypy strict mode

**Impact:** `uv run mypy src/` will fail on the new file, blocking quality gate.

**Source:** Story Dev Notes, validation code block

**Problem:**
The function signature shows `technology_set: TechnologySet` (not nullable), but the body contains `if technology_set is None: return warnings`. Under `mypy --strict`, this `None` check against a non-optional type is an error. The correct type is `technology_set: TechnologySet | None`.

The `validate_and_log` integration helper correctly uses `TechnologySet | None`, but the primary `validate_population_for_technology_set` function in the story does not. A developer copying the story's code snippet verbatim will produce a mypy failure.

**Recommended Fix:**
Change the function signature to `technology_set: TechnologySet | None` in the Dev Notes code block. Also update the test example that passes `technology_set = None`.

### 3. Note that dictionary encoding uniqueness check uses `.dictionary.to_pylist()`

**Value:** Prevents a subtle PyArrow bug where null-encoded values appear in the unique set.

**Suggestion:**
The dictionary `unique_values = set(incumbent_col.dictionary.to_pylist())` returns ALL dictionary values, including ones that may not be present in any row (if the dictionary was pre-built with extra entries). The safer pattern is:
```python
unique_values = set(incumbent_col.unique().dictionary.to_pylist())
```
Or cast to non-dictionary first: `set(pc.unique(incumbent_col).to_pylist())`. Add a note about this edge case.
