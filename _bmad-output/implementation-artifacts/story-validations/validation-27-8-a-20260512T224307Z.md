### Technical Alignment

**Status:** ⚠️ Partially Misaligned

- **`null` as Record key (JavaScript bug):** The implementation detail code block shows `null: "source"` as an object key. In JavaScript, object keys are always strings; `null` key becomes `"null"` string. A lookup with `map[null]` won't find `map["null"]` entry at runtime. This is a subtle bug that will cause the migration to silently fail for the most common legacy case (user with no sub-view = library default).

### 2. `LEGACY_POPULATION_SUBVIEW_MAP` null-key is a JavaScript Runtime Bug

**Impact:** Migration silently fails for the most common case: a user with the default library view (`activeSubView === null`) will NOT be migrated to `"source"` because `null` as an object key becomes the string `"null"`, and the lookup `map[null]` returns `undefined`, not `"source"`.
**Source:** Dev Notes — Implementation Details code block

**Problem:**
```typescript
// BUG: Object key `null` becomes string "null" at runtime
const LEGACY_POPULATION_SUBVIEW_MAP: Record<string, PopulationSubView | null> = {
  null: "source",  // ← this key is actually "null" (string), not null (JS value)
  ...
};
// Runtime: LEGACY_POPULATION_SUBVIEW_MAP[null] === undefined, not "source"
```

**Recommended Fix:**
Replace the map lookup in migration logic with an explicit null guard:
```typescript
function migratePopulationSubView(value: SubView | null): SubView {
  if (value === null) return "source";
  return LEGACY_POPULATION_SUBVIEW_MAP[value] ?? value;
}
```
Note that the `Record<string, ...>` type annotation can still be kept for the non-null entries.
