### 1. Badge variant changes are testable via existing `data-variant` pattern — mention it

**Value:** Gives developer a lightweight regression path rather than "check in browser"

The badge component renders `data-variant={variant}` on its `<span>`. `ScenarioCard.test.tsx:113` already demonstrates this pattern:
```ts
expect(badge).toHaveAttribute("data-variant", "warning");
```
Since no `PolicyCard.test.tsx` exists and the story correctly says no new tests are required, the testing strategy could at minimum mention that the `data-variant` attribute is the mechanical verification path should future tests be added, or allow the developer to write a simple render test if they choose. Currently the Testing Strategy section says only "Manual verification in browser" — this is accurate but misses pointing to the existing test pattern.

### 2. Task 3.1 grep pattern returns ~20 false positives

**Value:** Developer saves time distinguishing legitimate default-variant badges from problematic ones

Task 3.1 suggests:
```
grep -r 'variant="default"' frontend/src/components
```
This returns ~20 results including legitimate uses like `<Badge variant="default">5 policies</Badge>` (PoliciesStageScreen.tsx:1079), `<Badge variant="default">Unchanged</Badge>` (ParameterRow.tsx:45), etc. Only 3 results have the problematic `bg-*` override pattern.

More targeted command:
```
grep -r 'variant="default".*bg-' frontend/src/components
```
This returns exactly the 3 lines the story intends to fix (PolicyCard.tsx:271, PolicyCard.tsx:278, PoliciesStageScreen.tsx:1086).
