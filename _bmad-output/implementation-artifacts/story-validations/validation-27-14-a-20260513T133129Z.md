### 1. Badge appearance changes not validated for user acceptability

**Impact:** The story changes error and editing badges from dark backgrounds (`bg-red-500`, `bg-blue-500`) to light backgrounds (`bg-red-50`, `bg-sky-50`) without explicit validation that this appearance change is acceptable. Error badges especially may need to be visually prominent, and the lighter variant may not provide sufficient visual weight.

**Source:** AC-1, AC-2 (Dev Notes section)

**Problem:**

The appearance change is noted as "intentional" in Dev Notes but not validated. The `destructive` variant uses light red (`bg-red-50 text-red-700`) instead of the current dark red (`bg-red-500 text-white`). While this aligns with the Badge design system, it significantly changes the visual prominence of error indicators. The same issue applies to the editing badge changing from dark blue to light blue (`bg-sky-50`).

From Badge component:
```tsx
destructive: "border-red-200 bg-red-50 text-red-700"  // Light
info: "border-sky-200 bg-sky-50 text-sky-700"        // Light
```

Current usage:
```tsx
<Badge variant="default" className="...bg-red-500 text-white">     // Dark
<Badge variant="default" className="...bg-blue-500 text-white">    // Dark
```

**Recommended Fix:**

Add explicit validation step OR add an AC confirming the lighter appearance is acceptable:

```
AC-X: Given the designer/stakeholder reviews the new badge appearances, when presented with the lighter background variants (destructive, info, secondary), then the appearance is confirmed as acceptable for error, editing, and active indicators.
```

OR, if the darker appearance is required, add new variants to Badge component instead of using existing light variants.
