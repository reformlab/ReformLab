**Location**: Same file - "Eligibility Invariance Pattern" section (lines 351-377)
**Change**: Corrected mechanism description from `eligible_indices` to `EligibilityMergeStep`
**Before**:
```
**Implementation Note**: The existing `apply_choices_to_population()` already handles this correctly via the `choice_result.chosen` alignment with `eligible_indices`. Story 28.3's incumbent writeback follows the same pattern — only eligible households receive new incumbent values.
```
**After**:
```
**How it works** (from eligibility.py:263-420):
The `EligibilityMergeStep` runs BETWEEN `logit_choice` and `StateUpdateStep`. It expands N_eligible choices to N_total by filling ineligible rows with `default_choice` (typically `"keep_current"`).

**Pipeline ordering requirement**: `StateUpdateStep.depends_on` must include `"eligibility_merge"` when eligibility filtering is active.

**Implementation mechanism**:
1. `DiscreteChoiceStep` filters population to eligible households only
2. `LogitChoiceStep` computes choices for filtered population
3. `EligibilityMergeStep` expands choices back to N_total, filling ineligible rows with `default_choice="keep_current"`
4. `StateUpdateStep` receives full population with expanded ChoiceResult
5. `apply_choices_to_population()` writes incumbents, but the `keep_current` skip-rule preserves actual technology values for ineligible households
```
