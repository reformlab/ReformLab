## 🐛 Correctness & Safety

### 🎭 Lying/Weak Tests

**Finding 1: `test_decision_column_in_first_year_only_fills_null_in_second` and `test_decision_column_in_second_year_only_fills_null_in_first` — incomplete null-fill assertions**

When `_build_decision_columns` runs for a year with a decision record, it injects **four** columns onto the table:
- `{domain}_chosen` (string)
- `{domain}_probabilities` (list\<float64\>)
- `{domain}_utilities` (list\<float64\>)
- `decision_domains` (list\<string\>)

Both Tests 1 and 2 only assert null fill for `heating_chosen`. The `heating_probabilities`, `heating_utilities`, and `decision_domains` columns are entirely unchecked. The `decision_domains` column is especially meaningful here — it's a `list<string>` type, and permissive promotion on list-typed columns has subtler semantics than on primitive columns. If this column were to change type under promotion (or not null-fill correctly), these tests would not catch it.

- 📍 `tests/orchestrator/test_panel.py:799–805` (Test 1 assertions)
- 📍 `tests/orchestrator/test_panel.py:861–868` (Test 2 assertions)

**Finding 2: AC-2 coverage is asymmetric — "column in year-2 only" case is unimplemented**

AC-2 reads: *"when a test feeds tables with a data output column present in one year and absent in another."* Tests 1 and 2 cover both directions for decision columns (year-1 only, then year-2 only). Test 3 covers only the "output column present in year-1, absent in year-2" direction. The symmetric case — output column present in year-2, absent in year-1 — is entirely absent. This is not equivalent behavior from PyArrow's perspective: the promoted column type comes from whichever year defines it first, so the order can matter for schema inference.

- 📍 `tests/orchestrator/test_panel.py:870–919`

**Finding 3: Type-mismatch test only goes through the non-decision branch**

`test_int_float_type_mismatch_promotes_to_float` constructs two `YearState` objects with no decision records → `has_any_decision_columns = False` → takes the `else` branch at `panel.py:162` (line 163). The `elif has_any_decision_columns` branch at line 155–160 is never exercised with a type mismatch. Both branches call `pa.concat_tables(..., promote_options="permissive")` identically, but the story's motivation is to lock *both* code paths as regression tests. AC-3 doesn't say which branch, but the semantic split between branches exists precisely because their table structures diverge; a type-mismatch test that forces the decision branch would be more complete.

- 📍 `tests/orchestrator/test_panel.py:921`

**Finding 4: `pa.types.is_floating()` is a weak type assertion**

`pa.types.is_floating()` returns `True` for `pa.float16()`, `pa.float32()`, and `pa.float64()`. The story dev notes explicitly state "int64 + float64 → float64" as the expected promotion. If a future PyArrow version changes promotion behavior (or the test is ported to a version that promotes to float32), this assertion would still pass silently. The correct assertion is `assert panel.table.schema.field("income").type == pa.float64()`.

- 📍 `tests/orchestrator/test_panel.py:963`

**Finding 5: Test 4 only checks year-2024 values, not year-2025 float values**

The test verifies `year_2024_rows.column("income").to_pylist() == [50000.0, 60000.0, 70000.0]` (int-promoted-to-float). It does not check that year-2025 float values `[52000.5, 62000.5, 72000.5]` are preserved without truncation or precision loss. The test documents only half the promotion round-trip.

- 📍 `tests/orchestrator/test_panel.py:965–966`
