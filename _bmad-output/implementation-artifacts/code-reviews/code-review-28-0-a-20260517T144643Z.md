## 🏛️ Architectural Sins

### [10/10] Non-Existent Base Class: `ReformLabError`

The ADR's Error Hierarchy section defines:

```python
class DiscreteChoiceError(ReformLabError):  # ← DOES NOT EXIST
```

**Reality:** `grep -r "ReformLabError" src/` → **zero results**. The actual `DiscreteChoiceError` inherits from plain `Exception`. There is no project-wide base error class. An implementor following this ADR as-written would hit a `NameError` on first import.

- 📍 `_bmad-output/planning-artifacts/spike-investment-decisions-technology-set.md:1111`
- 📍 `src/reformlab/discrete_choice/errors.py:15` — actual: `class DiscreteChoiceError(Exception):`
- 💡 Fix: Either remove the `ReformLabError` reference and inherit from `Exception` (matching today's code), or document as a prerequisite that `ReformLabError` must first be created in a separate subtask of 28.1.

### [9/10] `domain.alternative_ids` Called on `DecisionDomain` Protocol — Property Doesn't Exist

Two distinct code snippets in the ADR call `.alternative_ids` on a `DecisionDomain` object:

**In `validate_incumbent_column()`:**
```python
valid_ids = domain.alternative_ids  # tuple[str, ...]  ← WRONG
```

**In `IncumbentUpdateStep.execute()`:**
```python
valid_ids = self._domain.alternative_ids  # ← WRONG
```

**Reality:** `DecisionDomain` protocol (`domain.py:23-64`) exposes only `alternatives: tuple[Alternative, ...]`. The `alternative_ids` computed property exists on `ChoiceSet` (types.py:72-75), not on the domain. This is a runtime `AttributeError` in both call sites.

- 📍 `_bmad-output/planning-artifacts/spike-investment-decisions-technology-set.md:241` (validate_incumbent_column)
- 📍 `_bmad-output/planning-artifacts/spike-investment-decisions-technology-set.md:638` (IncumbentUpdateStep)
- 📍 `src/reformlab/discrete_choice/domain.py:35-43` — domain only exposes `name`, `alternatives`, `cost_column`, `apply_alternative`
- 💡 Fix: Replace with `{alt.id for alt in domain.alternatives}` at both call sites. Story 28.2/28.3 implementors will introduce bugs if they follow this verbatim.

### [6/10] `TechnologySet.domains: dict[str, ...]` Violates Frozen Dataclass Immutability

```python
@dataclass(frozen=True)
class TechnologySet:
    domains: dict[str, DomainTechnologySelection]  # ← mutable container
```

Frozen dataclasses prevent field reassignment but do NOT prevent mutating the dict itself (`technology_set.domains["new_key"] = ...` is perfectly legal). Every other frozen domain type in the project uses `frozenset` for set fields and `tuple` for sequence fields. This is the first mutable container field on a frozen dataclass in the codebase. mypy strict will not flag this, but it's semantically incorrect per project conventions.

- 📍 ADR Decision 1 schema definition, line ~79
- 📍 `src/reformlab/discrete_choice/types.py:178` — `TasteParameters.calibrate: frozenset[str]` as the correct pattern
- 💡 Fix: Use `Mapping[str, DomainTechnologySelection]` (read-only view) or `tuple[tuple[str, DomainTechnologySelection], ...]` and provide a dict-view property. More pragmatically, annotate as `Mapping` and construct from a dict via `MappingProxyType`.

### `null` JSON Key in Manifest Example Is Invalid JSON (RFC 8259)

```json
"from_to": {
    null: {"ev": 500},   ← INVALID — JSON keys must be strings
```

Python's `json.dumps({None: {"ev": 500}})` produces `{"null": {"ev": 500}}` (the string `"null"`), not a JSON null key. Any implementor treating the example as a schema specification will produce different output than the serialization code would generate. The `TransitionLog.from_to: dict[str | None, dict[str, int]]` type annotation is fine in Python, but its JSON representation needs to be explicitly addressed.

- 📍 ADR Decision 5, manifest JSON snippet, line ~753
- 💡 Fix: Show the actual JSON output (`"null"` as string key or explicitly encode `None` as `"__unknown__"`) and add a note about the serialization bridge.

## ⚡ Performance & Scalability

### [Medium Impact] `ChoiceResult.chosen.to_pylist()` on Large Populations

`TransitionLog.from_choice_result()` calls both `choice_result.chosen.to_pylist()` and `incumbent_column.to_pylist()` before iterating. For a 50k-household population this materializes two full Python lists. This is already the pattern used in existing domain_utils, so it's not a regression — but for a new type specifically described as capturing per-period aggregates, a PyArrow `value_counts()` or groupby approach would be O(N log N) with less memory allocation. Worth noting as a future optimization risk at scale.

> 2. `LogitChoiceStep` → draws choices

**Appendix Example 1 (code):**

steps.extend([

    VehicleStateUpdateStep(..., name="vehicle_state_update"),
    IncumbentUpdateStep(..., name="vehicle_incumbent_update"),

The positions are swapped. The code is probably correct (DecisionRecord should capture after all updates), but the narrative is wrong. ### "Domain Not in technology_set" Has Two Contradictory Semantics

**`to_choice_set()` implementation (Decision 1, line ~94-96):**
```python
if domain not in self.domains:
    return ChoiceSet(alternatives=full_alternatives)  # full list, domain IS run
```

**Pipeline builder (Appendix Example 1, line ~1209):**
```python
if technology_set is None or "vehicle" in technology_set.domains:
    # add vehicle steps  → domain is SKIPPED when not in technology_set
```

These are mutually exclusive semantics. If `technology_set = TechnologySet(domains={"heating": ...})`, then:
- `to_choice_set("vehicle", ...)` says: run vehicle with full alternatives
- `build_step_pipeline()` says: skip vehicle entirely

Story 28.1/28.3 implementors will be forced to choose one semantic, and they'll choose different ones.

### Duplicate Reference-Alternative Discovery Algorithms With No Shared Implementation

The ADR defines two separate functions that compute the same thing (the default incumbent when column is absent) with slightly different logic:

1. `assign_default_incumbents()` → calls `_find_reference_alternative(domain)` (priority: "keep_current" → contains "keep" → first)
