## 🐛 Correctness & Safety

### Bug 1 (CRITICAL): AC-4 Protection Only Covers One of Two Triggers

📍 `frontend/src/contexts/AppContext.tsx:538-595`

The `isDefaultPopulationSelection` ref guards against auto-rename **only** when the auto-name effect is triggered by the default-selection effect changing `selectedPopulationId`. It does **not** guard the trigger from `activeScenario?.id` changing (which is also in the dep array at line 589).

**Concrete reproduction:**

1. User calls `loadSavedScenario("id")` → `setActiveScenario(found)` called
2. `activeScenario?.id` changes → **auto-name effect fires immediately**
3. At this point `isDefaultPopulationSelection.current = false` (populations already loaded, flag was cleared earlier)
4. `isManuallyEdited = false` (restored scenario not in `manuallyEditedScenarioNames`)
5. Guard `if (isDefaultSelection && !isDefaultName)` = `if (false && ...)` = **no protection**
6. `generateScenarioSuggestion(null, selectedPopulationId, ...)` generates `"Untitled (FR Synthetic 2024)"`
7. Curated name `"My Curated Scenario"` → **silently overwritten**

The `loadSavedScenario` function (line 608-618) does not add the loaded scenario to `manuallyEditedScenarioNames`, leaving restored scenarios fully exposed to auto-renaming the moment their ID hits the dep array. The fix attempted for AC-4 only works when the default-selection effect fires BEFORE the auto-name effect in the same render batch, which is only guaranteed when `selectedPopulationId` starts empty.

### Bug 2 (IMPORTANT): `isDefaultPopulationSelection` Flag Leaks on Early Returns

📍 `frontend/src/contexts/AppContext.tsx:546, 549`

Both early-return guards exit the auto-name effect without clearing `isDefaultPopulationSelection.current`:

```typescript
if (isDemo) return;           // line 546 — flag NOT cleared
if (isManuallyEdited) return; // line 549 — flag NOT cleared
```

**Scenario:** Default-selection effect fires while demo scenario is active. The flag is set to `true`. Auto-name effect runs, hits `if (isDemo) return` — exits without clearing. Now `isDefaultPopulationSelection.current = true` indefinitely.

The user then calls `createNewScenario()`. A new scenario is set. Auto-name effect fires. Reads `isDefaultSelection = true`. The new scenario starts with name `"Untitled (FR Synthetic 2024)"` (default name), so `isDefaultName = true`. Guard: `if (true && !true)` = false — doesn't block. OK in this case. BUT if the user had already renamed the new scenario (unlikely at creation, but possible if there's a race), the stale flag would block the rename.

Riskier: if templates or populations change AFTER an early return that didn't clear the flag, the next auto-name effect run has a stale `true` flag protecting against a rename that should happen.

### Lying Test 1: AC-4 "My Scenario keeps its name"

📍 `frontend/src/contexts/__tests__/AppContext.integration.test.tsx:470-524`

The test calls `getState().setActiveScenario(testScenario)` outside of `act`. The first `waitFor` polls between the state update and the auto-name effect, catching the window where `name = "My Scenario"` before the effect renames it to `"Untitled (FR Synthetic 2024)"`. The second `waitFor` checks `selectedPopulationId`, which was **already set** before the test, so it resolves immediately — before the auto-name effect is fully flushed.

The final synchronous assertion `expect(name).toBe("My Scenario")` asserts on state that has likely already been mutated by the effect, but it runs before the microtask queue is flushed. The test **does not** prove the scenario was protected; it proves there's a race-condition window.

```typescript
getState().setActiveScenario(testScenario); // no act() wrapper
await waitFor(() => {
  expect(name).toBe("My Scenario"); // races against auto-name effect
});
await waitFor(() => {
  expect(selectedPopulationId).toBe("fr-synthetic-2024"); // already set, resolves instantly
});
expect(name).toBe("My Scenario"); // sync check — effect may or may not have fired
```

## 🔧 Maintainability Issues

**`TestAppWithStateAccess` anti-pattern:**  
📍 `AppContext.integration.test.tsx:107-117`  
The `onStateReady(state)` callback fires on every render of the component. If any expensive operation (logging, DOM mutations) were in the callback, it would create perf issues. More importantly, it can cause "state update during render" warnings if the callback triggers external state changes.

**Better pattern:** Use `useEffect(() => { onStateReady(state); }, [...relevantState])` or a ref-based approach.
