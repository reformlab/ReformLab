The story correctly adds `console.warn(...)` at `usePortfolioDialog.ts:293` when template lookup fails. But the story also says: *"No new unit tests needed — this is a cleanup story with behavior-preserving changes."*

The existing `usePortfolioDialog.test.ts` covers happy-path load behavior but not the template-not-found branch. A single `vi.spyOn(console, 'warn')` test would lock this in.

## 🔧 Maintainability Issues

### Badge audit used a pattern that was too narrow

Task 3 used: `grep -r 'variant="default".*bg-' frontend/src/components`

This finds only bypasses that combine `variant="default"` WITH a `bg-*` class on the same element — which is exactly the 3 known bypasses. It misses `variant="default"` usages that are semantically incorrect but happen not to have bg-* overrides.

Two instances that survived the audit:

- `PolicyCard.tsx:298`: `<Badge variant="default" className="text-xs shrink-0">…params</Badge>` — the params count badge carries semantic meaning (informational count) but uses the generic default variant when `variant="outline"` or `variant="secondary"` would be more appropriate.
- `PoliciesStageScreen.tsx:1084`: `<Badge variant="default" className="text-xs shrink-0">{p.policy_count} policies</Badge>` — same issue.

These don't violate AC-4's letter but violate its spirit. The cleanup story's own audit should have surfaced them for a documented rationale.

### Unnecessary `<>` Fragment wrapper around warning JSX

Before this story, the conditional was:
```tsx
{populationColumnWarnings.length > 0 ? (
  <div className="...">...</div>
) : null}
```

After:
```tsx
{populationColumnWarnings.length > 0 ? (
  <>
    {/* comment */}
    <div className="...">...</div>
  </>
) : null}
```

The Fragment was added solely to host the JSX comment. A regular code comment placed before the ternary expression would have been cleaner and not changed the component's JSX structure:

```tsx
{/* Multi-paragraph warning structure is intentional:
  * heading improves scannability; separate <p> elements
  * group problem statement from action item for accessibility.
  * Four lines of explanation as required by AC-5. */}
{populationColumnWarnings.length > 0 ? (
  <div className="...">...</div>
) : null}
```

This also fixes the AC-5 line-count issue.

### Quality gate transparency: "pre-existing test failures" not enumerated

The Dev Agent Record states: *"Pre-existing test failures are unrelated to this story's changes"* — but doesn't list which tests fail, which test files, or why they're considered pre-existing.

For a cleanup story whose explicit purpose is reducing technical debt, this is insufficient. If the failures are genuinely unrelated, they should be listed so they can be tracked (ideally as separate deferred items or confirmed as known flakiness).
