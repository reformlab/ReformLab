## 🐛 Correctness & Safety

- **🐛 Duplicate column corruption in `add_incumbent_columns_to_population`:**
  The function calls `table.append_column("incumbent_heating", ...)` unconditionally whenever `heating_type_col` is absent — but there is **no guard** checking whether `incumbent_heating` already exists in the table. PyArrow permits duplicate column names: `pa.table({"a": [1]}).append_column("a", pa.array([2]))` produces a valid 2-column table where both columns are named `"a"`. The function will silently produce a malformed table whenever called on a population that already carries these columns (user uploads, re-runs, data fusion pipelines calling it twice). Downstream `table.column("incumbent_heating")` will return the first column; the second is silently ignored — but schema checks, Parquet writes, and `column_names` assertions will behave unexpectedly.
  - 📍 `src/reformlab/discrete_choice/population_validation.py:171-209`
  - 🔄 Reproduction: `add_incumbent_columns_to_population(pop_already_with_incumbents)` → table with `["...", "incumbent_heating", "incumbent_vehicle", "incumbent_heating", "incumbent_vehicle"]` schema.

- **🐛 Circular import workaround introduces hidden fragility:**
  `step.py:238` uses `from reformlab.discrete_choice import validate_population_for_technology_set` inside `execute()` to avoid a `step.py → __init__.py → step.py` circular dependency. The deferred lazy import works at runtime but the underlying circular dependency is a time bomb. Module import order changes (e.g., a future `__init__.py` reorder) can reintroduce `ImportError`. The correct fix is to import directly from `reformlab.discrete_choice.population_validation`.
  - 📍 `src/reformlab/discrete_choice/step.py:238`
  - 🔄 Reproduction: Unlikely today but surfaces if import order changes.
