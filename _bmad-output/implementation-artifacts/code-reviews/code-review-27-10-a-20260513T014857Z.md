## 🐛 Correctness & Safety

- **🐛 Bug — `formatLargeNumber(Infinity)` → "InfinityB":**
  - 📍 `frontend/src/utils/formatters.ts:193`
  - 🔄 Reproduction: `formatLargeNumber(Infinity)` → `abs = Infinity` → `abs >= 1e9` is `true` → `(Infinity / 1e9).toFixed(1)` = `"Infinity"` → returns `"InfinityB"`. Same for `-Infinity` → `"-InfinityB"` (since `Math.abs(-Infinity) >= 1e9`). The `value / 1e9` path returns `Infinity`, and `toFixed` on `Infinity` returns the string `"Infinity"`. Fix: add `if (!Number.isFinite(value)) return value > 0 ? "∞" : "-∞";` after the NaN guard.

- **🎭 Lying Tests — locale-sensitive exact-string assertions without locale pin:**
  - 📍 `frontend/src/utils/__tests__/formatters.test.ts:19,57,110,131`
  - 🤥 Why they lie: `formatNumber(1234.56)` uses `Intl.NumberFormat(undefined, ...)` which reads the **host OS locale**. `toBe("1,235")` only holds in an English locale. On macOS with French language, `Intl.NumberFormat` formats as `"1 235"` (non-breaking space + no comma). Similarly `formatDate("2026-05-13")` asserts `"May 13, 2026"` which is English-only. The tests pass in English CI but are untested failures waiting for any non-English contributor or CI runner. Fix: pass `locale: "en-US"` to each formatter call in tests, or set `process.env.LANG = "en-US"` in the test setup file.

- **🐛 Bug — `formatCurrency` negative handling is locale-fragile:**
  - 📍 `frontend/src/utils/formatters.ts:84-88`
  - 🔄 Reproduction: In a locale that formats negative numbers with trailing minus (e.g., `fi-FI`) or parentheses (accounting style), `formatted.startsWith("-")` is `false`. The code then sets `sign = "-"` (from `value < 0`) but `absFormatted` still contains the locale's negative representation, producing something like `"-€(1,235)"` or `"-€1 235-"`.
