Beyond DRY, the copies diverged — `ResultsOverviewScreen.tsx` forgot `useCallback` on `handleCopy` while `RunSelector.tsx` and `ResultsListPanel.tsx` have it. This is exactly the pattern the story's own dev notes tried to avoid ("No new files (uses helpers from Story 27.10)").

  - 📍 `frontend/src/components/comparison/RunSelector.tsx:32-78`
  - 📍 `frontend/src/components/screens/ResultsOverviewScreen.tsx:38-84`
  - 💡 Fix: Extract `RunIdDisplay` to `frontend/src/components/shared/RunIdDisplay.tsx` (one source of truth). The `ResultsOverviewScreen` version is the odd one out — it needs `useCallback` added.

## 🐍 Pythonic Crimes & Readability

- **Unit-label logic is over-aggressive:** `getColumnLabel` in `FiscalTab.tsx` falls through to the `metaCols.includes(col)` branch for ANY meta column and appends `(€)`. The mock comparison response fixture in the very same test file proves this is wrong: `columns: ["year", "metric", "Policy A", "Policy B"]` — "year" and "metric" are categorical identifiers, not monetary amounts. "year (€)" will appear in production.
  - 📍 `frontend/src/components/comparison/FiscalTab.tsx:49-54`
  - Same problem in `WelfareTab.tsx` for unknown meta columns.
  - 💡 Fix: Add an explicit allowlist for non-monetary meta columns (`year`, `metric`, `category`, `decile`, `name`) and only apply `(€)` to columns not in that list, or apply units per-column based on a column-name regex/suffix rule.

## ⚡ Performance & Scalability

- **[Low] Three `results.filter()` passes in render:** `ComparisonDashboardScreen.tsx:194-199` iterates `results` three times in the same JSX render block to check for failed runs, count completed, and count failed. For typical run counts this is trivial, but it can be a single pass.
  - 📍 `frontend/src/components/screens/ComparisonDashboardScreen.tsx:194-199`
  - 💡 Fix: Extract before the JSX: `const failedCount = results.filter(r => r.status === "failed").length; const completedCount = results.filter(r => r.status === "completed").length;` — or use a single `reduce`.

## 🐛 Correctness & Safety

- **🐛 Bug (Dead code):** The `runResult ?` fallback skeleton in the Detail tab (lines 357-365) is unreachable code. `handleTabChange` calls `setActiveTab("detail")` and then `void loadDetail()` synchronously. `loadDetail()` calls `setDetailLoading(true)` before its first `await`. React 18 automatic batching commits both state updates in the same render cycle, so when the Detail tab content renders for the first time, `detailLoading` is already `true` — the first skeleton block (lines 345-352) fires, not the fallback. The duplicate skeleton only hides a subtle assumption about React's batching behavior.
  - 📍 `frontend/src/components/screens/ResultsOverviewScreen.tsx:357-365`
  - 🔄 Reproduction: React 18 + concurrent mode, click Detail tab → always hits `detailLoading` branch, never reaches `runResult ?` branch.

- **🐛 AC-6 Incomplete Reset:** When `activeScenarioId` changes, `viewMode` (absolute/relative), `activeTab` (distributional/fiscal/welfare), and `detailTarget` (open detail panel) are NOT reset. A user who had set Relative mode on Fiscal tab with a detail panel open will see those states persist when switching scenarios. AC-6 specifies "both are reset" (selectedRunIds + comparisonData) so the letter of the AC is met, but the spirit of "not seeing comparison from a previous scenario" is violated for UI state.
  - 📍 `frontend/src/components/screens/ComparisonDashboardScreen.tsx:74-78`
