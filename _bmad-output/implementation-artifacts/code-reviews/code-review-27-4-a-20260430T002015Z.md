## ⚡ Performance & Scalability

- **[MEDIUM] `useEffect([composition])` + `setComposition()` = guaranteed extra render cycle:** The backward-compat effect fires every time `composition` changes. After scaffolding runs and calls `setComposition()`, `composition` changes, so the effect fires *again* (finding nothing to scaffold and returning early). This means every scaffolding operation causes 2 effect invocations and 2 renders. For a composition of N legacy template entries, this is O(1) wasted renders per entry scaffolded — manageable now, but the pattern is inherently fragile. React's eslint rule `react-hooks/exhaustive-deps` will flag this.
  - 📍 `frontend/src/components/screens/PoliciesStageScreen.tsx:359`
  - 💡 Fix: Use a `useRef` set to track which `templateId`s have been scaffolded so the effect can be moved out of the `[composition]` dependency cycle, or extract the scaffolding to a one-shot `useEffect([])` on mount that checks once.

## 🐛 Correctness & Safety

- **🐛 Bug: Identity collision in backward-compat scaffolding effect.** The matching logic at line 336–340:
  ```ts
  results.find((r) =>
    r.status === "fulfilled" &&
    r.value &&
    (r.value.entryId === entry.instanceId || r.value.entryId === entry.templateId)
  )
  ```
  When a portfolio contains two instances of the same template (both lacking `instanceId`), `r.value.entryId` is set to `entry.templateId` for both (line 319: `entryId: entry.instanceId || entry.templateId`). Both scaffold results will have the same `entryId`. The `results.find()` call on each entry will match the *first* result for that `templateId`, so both entries get the same `editableParameterGroups` — but both should get identical groups anyway in this case, so the visible impact is low. **However**, if the user edits groups on one instance before the scaffold resolves, the stale composition snapshot in `setComposition(prev => ...)` means edits can be silently overwritten.
  - 📍 `frontend/src/components/screens/PoliciesStageScreen.tsx:319, 336–340`

- **🐛 Bug: Silent failure when template not in frontend state.** `addTemplateInstance` calls `getTemplate(templateId)` (async), then does `templates.find((tmpl) => tmpl.id === templateId)`. If the template is available in the backend but not yet loaded in the frontend `templates` array (e.g., race with `useTemplates()` refetch), the function returns at line 173 with no toast, no console error, nothing. The user clicks a template card, the API call succeeds (consuming network + server CPU), and the policy silently fails to appear.
  - 📍 `frontend/src/components/screens/PoliciesStageScreen.tsx:172–173`
