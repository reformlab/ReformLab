## Challenges and Growth Areas

### Partial Feature Releases Persist
**Issue:** Multiple stories shipped with partially implemented features claimed as complete.

**Examples:**
- **Story 28.1:** AC-6 (Contract roundtrip test) — core infrastructure implemented but integration test not written
- **Story 28.4:** AC-4 (Population incumbent detection) — stub with empty sets, no AppContext integration
- **Story 28.4:** AC-9 (Orphan-ASC validation) — stub always returns empty array
- **Story 28.5:** AC-1, AC-3, AC-4, AC-9 — tests marked complete but were stubs (fixed via synthesis)

**Root Cause:** Task checkboxes marked complete without verifying end-to-end functionality. AC completion criteria accepted helper functions as "implementation" without validating production wiring.

**Impact:** Analysts cannot use population-aware features in wizard; regression tests don't validate actual invariants.

**Recommended Action:** Adopt "Zero Partial Feature Releases" process agreement — before marking story done, verify all ACs are production-wired (not just helper functions).

### Migration Scope Underestimation
**Issue:** Story 28.1's AC-9 claimed all `.toLocaleString()` calls migrated to centralized formatters, but only ~15% were actually completed.

**Evidence:** Task explicitly stated "migrate all instances" but implementation only covered 7 components. 38 instances remain in 22 files.

**Root Cause:** Scope misestimation — task enumerated 26 files but implementation only covered obvious components. grep enumeration wasn't performed before claiming completion.

**Impact:** Future formatter changes require touching many more files. Inconsistent number/currency/date formatting across application.

**Status:** Deferred as AI Review action item. Requires dedicated PR to migrate remaining files.

### Stub Implementations in Regression Tests
**Issue:** Story 28.5 (Epic closing regression) had multiple acceptance criteria marked complete with stub tests:
- AC-1: Chaining invariant test didn't validate actual `incumbent_t == chosen_{t-1}` equality
- AC-3: Transition-counts fixture never loaded or compared
- AC-4: No-decisions baseline test was stub
- AC-9: Nightly test was unconditional skip

**Root Cause:** Test structure written but validation logic not implemented. Reviews correctly flagged as "tests don't validate their claims."

**Resolution:** Code review synthesis identified all issues; fixes applied to implement actual validation logic where possible, document limitations where deferred.

### Alternative ID Reconciliation Technical Debt
**Issue:** Heating domain has two incompatible alternative ID sets:
- Legacy IDs (heating.py): `gas_boiler`, `heat_pump`, `electric`, `wood_pellet`
- DEFAULT_TECHNOLOGY_SET IDs: `condensing_boiler`, `heat_pump_air`, `heat_pump_ground`, `district_heating`

**Impact:** Story 28.3 explicitly documented this mismatch. Populations created with legacy IDs will show validation errors. Wizard's "Add to set" action creates mixed technology sets.

**Status:** Documented in multiple story files as "out of scope for this story." Reconciliation deferred to future work.

**Recommended Action:** Create dedicated story to migrate heating domain to DEFAULT_TECHNOLOGY_SET IDs before production release.

### Frontend Integration Gaps
**Issue:** Story 28.4's Technology step has population-aware features (AC-4, AC-5, AC-6, AC-7) that are completely non-functional:
- `populationId` hardcoded to `null`
- Population incumbents hardcoded to empty sets
- Mismatch warnings never show actual data
- "Add to set" action scaffolds alternatives without real household counts

**Root Cause:** Story was purely frontend; consumed APIs from Story 28.1 but didn't integrate with AppContext for real population data.

**Impact:** Analysts see UI elements that appear functional but don't work with actual populations.

**Status:** Documented as deferred work in AI Review follow-ups. Requires AppContext integration and population profile API extension.

## Key Insights

1. **AI Review Synthesis is Critical Net Positive** — Consistently caught production bugs (data corruption, type safety gaps, lifecycle issues) that would have reached users. Worth the additional review cycle time.

2. **Partial Feature Release Pattern Repeated** — Epic 27 had AC-5 production gap; Epic 28 has multiple stub implementations claimed as complete. Process change needed: verify end-to-end wiring before marking ACs done.

3. **Consolidation Requires Verification** — Story 28.1's formatter migration claimed 100% but only achieved ~15%. Need automated verification (grep enumeration) before claiming "all X migrated" completion.

4. **Alternative ID Debt is Ticking Time Bomb** — Incompatible ID sets between legacy heating domain and TechnologySet will cause user-visible errors. Should be reconciliation priority before production release.

5. **Regression Tests Must Actually Validate** — Story 28.5's stub tests demonstrate danger of claiming test coverage without validation logic. Reviews correctly identified this pattern.

6. **Frontend-Backend Integration is High Risk** — Story 28.4's non-functional population features show what happens when frontend story consumes backend APIs without integrating with actual data sources. Integration testing needed.

7. **Migration Testing Pays Off** — Every story that introduced breaking changes (28.1, 28.2, 28.3) included migration tests that caught regressions. Pattern: test legacy → current → migrated states.

8. **Documentation-Only Stories Need Same Rigor** — Story 28.0 (ADR) received code review synthesis that found pseudocode issues. Specification accuracy matters as much as code.

9. **Quality Gates Prevented Regressions** — All stories passing ruff/mypy/pytest/lint/typecheck before marking done caught issues that would have accumulated. Don't relax these.

10. **Epic Closing Stories Need Extra Scrutiny** — Story 28.5 had highest stub implementation count (4 ACs). Closing stories should get additional review validation.
