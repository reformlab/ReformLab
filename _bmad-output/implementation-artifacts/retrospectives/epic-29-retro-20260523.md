## Executive Summary

Epic 29 was a focused recovery epic, tracing its entire scope back to a single production hotfix on 2026-04-26 that narrowed `_DEFAULT_LIVE_OUTPUT_VARIABLES` after eight unmapped variables caused live run failures. All five stories completed in dependency order, restoring full variable coverage through a combination of custom TaxBenefitSystem extension work (29.1), systematic placeholder resolution (29.2), validation and integration (29.3), test hygiene sweep (29.4), and regression hardening (29.5).

Key achievements: four new custom OpenFisca variables live in a registered extension (`montant_subvention`, `eligible_subvention`, `malus_ecologique`, `aide_energie`), four generic-name placeholders replaced or removed with documentation, `_DEFAULT_LIVE_OUTPUT_VARIABLES` restored to 9 valid variables, all test fixtures swept clean, and schema-mismatch regression coverage added to the panel concatenation paths.

AI Code Review Synthesis ran across all five stories and continued to earn its place — catching runtime bugs (wrong GroupEntity API, boundary condition mismatch), tautological test assertions, test regressions from removed mappings, and vacuous-truth guards. The pattern is embedded and effective.

The primary concern carrying forward is a cluster of deferred ACs across three stories that represent real functional gaps: `malus_ecologique` silently returns 0 (input variable not injected), manifest extension tracking unimplemented, and multi-entity normalization not tested end-to-end. The "Zero Partial Feature Releases" agreement from Epic 28 was not enforced again.

Epic 30 has not been planned. A planning session is the immediate next step.

## What Went Well

### AI Review Synthesis Remains the Highest-Value Gate

Every story benefited materially from code review synthesis — not just catching cosmetic issues but real runtime bugs and AC gaps:

- **Story 29.1:** `menage.household_index` → `menage.count` fix (would have caused `AttributeError` at runtime for all custom variable computation); tautological assertion that always passed; duplicate `EXTENSION_VERSION` constant with sync risk
- **Story 29.2:** `test_normalization_regression.py` created `taxe_carbone` columns expecting `carbon_tax` output — mapping was removed, causing silent test failures; comment inaccuracy ("Removed" vs "Replaced")
- **Story 29.3:** Boundary condition `<=` vs `<` for income threshold in subsidy formula — would have produced incorrect eligibility results for households exactly at the threshold
- **Story 29.4:** Evidence score 1.2 (cleanest of the epic) — `irpp` in `test_result.py` renamed to `foyer_tax` to eliminate an ambiguous name
- **Story 29.5:** Vacuous-truth guards on null assertions added; symmetric AC-2 test added; type assertion tightened from `is_floating` to `== pa.float64()`

Five reviews, zero stories released with a known runtime bug left unfixed.

Story 29.3 introduced explicit pre-check tasks before any implementation work:


This pattern prevented false-confidence starts and would have surfaced the deferred `reformlab_malus_emissions` blocker immediately rather than mid-story. Worth standardizing.

### PM Decision Up-Front on aide_energie

It does — and this avoided building a duplicate formula from scratch. The verification command was documented directly in the story file, making it reproducible.

### Systematic Placeholder Categorization (Story 29.4)

Rather than mechanically replacing all occurrences of `irpp`, Story 29.4 first categorized each reference:

- **Mock data** → update to `irpp_economique`
- **Legitimate local variable** (holds `impot_revenu_restant_a_payer` values in integration tests) → leave unchanged with documentation
- **Intentional custom mapping fixture** → document with docstring
- **Arbitrary column name in mock data** → rename to semantically clear `foyer_tax`

This discipline prevented false positives and left the codebase in a cleaner state than a simple find-replace would have.

### Clean Dependency Chain Execution

The dependency sequence (29.1 ∥ 29.2 → 29.3 → 29.4 → 29.5) was designed in the story files and respected in execution. No story started before its prerequisites. The parallel 29.1/29.2 design was honored — both operated on disjoint variable sets.

### Zero User-Facing Regressions

Despite making substantive changes to `_DEFAULT_OUTPUT_MAPPING`, `_DEFAULT_LIVE_OUTPUT_VARIABLES`, the OpenFisca adapter initialisation, and 4 test files, no backward-incompatible changes reached end users. ## Challenges and Growth Areas

### Deferred ACs Pattern Persisted — Again

**Issue:** Three stories shipped with ACs marked incomplete. This is the third consecutive epic where the "Zero Partial Feature Releases" agreement was not honoured.

| Story | Deferred AC | Impact |
|-------|-------------|--------|
| 29.1 | AC#5 — formula behavior tests with boundary conditions | Missing test coverage for AC specification |
| 29.1 | AC#6 — manifest extension tracking | Manifest does not record which custom variables are active |
| 29.3 | AC#4 — normalization produces no ApiMappingError | No test proves full live path doesn't raise |
| 29.3 | AC#5 — English column names verified in normalized output | Custom variable English names unverified end-to-end |

**Root Cause:** AC completion criteria accepted helper functions or partial implementations. The multi-entity structure of OpenFisca variables (9 variables across 4 entities) made normalization testing harder than anticipated, leading to scope deferral mid-story rather than upfront.

**Recommended Action:** Before marking a story done, the question must be: "Can I show a user this working?" If normalization testing requires multi-entity plumbing not yet built, that's a blocker, not a deferral.

### malus_ecologique Silently Returns Zero

**Issue:** Story 29.1 implemented the `malus_ecologique` formula but identified that `reformlab_malus_emissions` (the vehicle CO₂ input variable) is not registered in the TaxBenefitSystem. The formula returns 0 for all households. This is a silent functional failure — no error is raised, but vehicle malus outputs are wrong for every household.

**Root Cause:** The formula accesses `menage('reformlab_malus_emissions', period)` but this input variable was never registered. Population data contains `vehicle_emissions_gkm` columns, but the bridge between population data and OpenFisca input variables was not implemented.

**Impact:** Any live run reporting `vehicle_malus` to analysts produces zeroes regardless of household vehicle profile. The story tracked this as a deferred item but did not capture it as a blocker for the epic-level acceptance criterion ("non-zero values for eligible households").

**Status:** Deferred from Story 29.1 into open debt. Must be resolved before `malus_ecologique` results can be trusted.

### Multi-Entity Normalization Gap

**Discovery in Story 29.3:** The 9 default output variables span 4 OpenFisca entities:
- `menage` (household): `revenu_disponible`, `impots_directs`, `prestations_sociales`, `montant_subvention`, `eligible_subvention`, `malus_ecologique`, `aide_energie`
- `foyer_fiscal` (tax household): `irpp_economique`
- `individu` (person): `salaire_net`

The `normalize_computation_result()` function processes a flat `pa.Table` from a single entity. Multi-entity normalization — assembling a household-level panel from variables computed at different entity levels — is not yet implemented. This caused ACs #4 and #5 of Story 29.3 to be deferred.

**Impact:** The full live path (adapter → multi-entity computation → normalization → result) has not been tested end-to-end. The integration test in 29.3 verifies that individual entity tables contain expected values, but does not exercise normalization.

**Root Cause:** The epic was scoped to restore variable names and add custom variables. Multi-entity normalization was an implicit architectural dependency that wasn't surfaced during epic planning.

### Pre-Existing mypy Errors Pollute Quality Gates

Multiple stories noted "mypy has pre-existing errors in `panel.py` unrelated to this story" and marked mypy as deferred. This creates a pattern where mypy is treated as optional rather than required.

**Impact:** The quality gate declared in CLAUDE.md (`uv run mypy src/`) is effectively bypassed. New mypy errors could accumulate undetected because the baseline is already dirty.

**Recommended Action:** The pre-existing `panel.py` mypy errors should be resolved in a dedicated story before they further erode mypy's signal.

### Evidence Score Variance Across Stories

Story 29.1 averaged 13.8 (REJECT) and Story 29.3 averaged 9.25 (CHANGES REQUESTED) — indicating implementation quality was lower for the more complex extension and validation stories. Stories 29.4 and 29.5 scored 1.2 and 3.3, consistent with their narrower scope.

**Pattern:** Higher-complexity stories (new architecture, API integration) need more synthesis scrutiny, not less. The current process applies uniform synthesis to all stories. Consider triggering extra reviewer attention when AC count > 5 or when the story touches a new architectural boundary.

## Key Insights

1. **Production hotfixes generate systematic debt** — The 2026-04-26 hotfix that narrowed `_DEFAULT_LIVE_OUTPUT_VARIABLES` spawned an entire five-story epic. Hotfixes should always be accompanied by a tracked debt item with explicit resolution scope.

2. **Custom OpenFisca variable patterns are now documented** — The formula-must-be-standalone-function constraint, `_create_variable_with_entity()` injection, and idempotency guard patterns are discoverable in Story 29.1's Dev Notes. Future extension work has a template.

3. **Input variable injection remains unsolved** — Population data has `vehicle_emissions_gkm` columns. OpenFisca formulas access data via `menage('variable_name', period)`. The bridge between these two worlds is not built. `malus_ecologique` is the first formula to expose this gap; any future formula that needs population-injected inputs will hit the same wall.

4. **Prerequisite verification tasks should be standard** — Story 29.3's pre-check pattern is more reliable than trusting that upstream stories are complete. Five bash commands before any implementation beats discovering a blocker mid-story.

5. **Categorize before replacing** — Story 29.4's systematic categorization of placeholder references (not just grepping and replacing) prevented false positives and produced more accurate documentation. This applies to any "sweep all X" consolidation task.

6. **Multi-entity normalization is unbuilt** — OpenFisca computes at multiple entity levels. The platform's normalization layer is household-centric. Any future story that adds a non-household variable (`irpp_economique` is already in this state) hits an untested normalization path. This is a significant architectural gap.

7. **Zero Partial Feature Releases requires a process enforcement mechanism** — Three epics, same pattern. Verbal agreements don't hold. The definition of done must include a mechanically verifiable check (e.g., "grep for TODO/DEFERRED/stub in story ACs returns 0 hits").

8. **Code Review Synthesis quality is inversely correlated with story complexity** — Simple stories (29.4: score 1.2, 29.5: score 3.3) had far fewer issues than complex stories (29.1: avg 13.8, 29.3: avg 9.25). This is expected but useful as a planning signal: allocate more synthesis attention to foundational or integration stories.
